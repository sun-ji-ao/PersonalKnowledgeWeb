> 后续需求修订：原有及上传的 Markdown 必须以 `.md` 文件保存，在线新写文章使用 HTML 正文与可视化编辑器。下面的实现能力和测试结论仅对应原 MVP；后续开发与存储规则以 [修订后的 PLAN.md](../technical-notes-lab/PLAN.md) 为准，不能将旧测试视为双格式功能已经通过。

## 决策标准

“最好不用静态库”按“不依赖静态站点生成和整站构建来发布文章”解释。Astro 也可以采用服务端渲染；不能因为项目使用 Astro，就断言它无法满足要求。真正的选择是保留现有阅读层并替换内容发布链路，还是在独立动态应用中建立新链路并迁移可复用资产。

| 标准 | 优先级 | 可核验的通过条件 |
| --- | --- | --- |
| 长文阅读 | 必需 | 长段落、目录、代码块、移动端宽度可读；文章有稳定公开地址 |
| Markdown 在线写作 | 必需 | 网页编辑正文，保存反馈明确，刷新后可继续编辑 |
| 直接上传 Markdown | 必需 | 导入 `.md` 正文及标题、摘要、标签；上传后保持草稿；错误有反馈 |
| 代码、数学、图表 | 必需 | Shiki 产生高亮，行内与块级公式排版，Mermaid 渲染；预览与公开正文使用一致规则 |
| 持久化与发布 | 必需 | 草稿写入数据库，重启后仍在；发布立即可读；未发布修改不进入公开快照 |
| 写作体验 | 高 | 自动保存、离开前保护、版本冲突反馈；常见编辑不会丢失内容 |
| 维护成本 | 高 | 依赖与部署简单、文档可重复执行；认证、备份和升级责任明确 |
| 原内容迁移 | 上线前必需 | 253 篇文章数量可对账；元数据、图片、链接、草稿状态和旧地址有映射及校验 |

## 已确认的原站事实

- 共 253 篇生成 Markdown；阅读层已有目录、分类、标签、归档、主题、复制代码、RSS 和 Pagefind 搜索。
- `package.json` 的发布链为导入、Astro 构建、Pagefind 建索引；`src/pages/docs/[...slug].astro` 使用 `getStaticPaths()`。
- `scripts/import_markdown.mjs` 第 423–424 行清空生成内容和图片目录。后台若直接写入 `src/content/docs`，下一次导入就可能覆盖新增内容。
- 同一导入脚本会剥离 frontmatter、删除开头标题、编号正文标题，并按目录与文件名重新生成元数据。它适合作为原专题文档整理器，不适合作为通用在线保存器。
- 原站公式渲染探针未产生数学排版；代码高亮探针通过。Mermaid 插件存在，但浏览器绘图验收尚未完成。
- 现站没有在线编辑器、文件上传 API、登录、数据库或发布快照。
- 历史日期含占位值和分配的展示日期；不能当作真实创作时间迁移。

详情与可定位证据见 [现有项目分析](./existing-project-analysis.md)。本评审另外只读核验了上述内容总量、导入清空行为和静态文章路由。

## 两条可行路线

| 比较项 | A：保留 Astro 阅读层，改 SSR + 内容后台 | B：独立动态应用，再迁移资产 |
| --- | --- | --- |
| 达成需求的可能性 | 可以；改为运行时读数据库并增加后台 | 可以；新方案直接围绕草稿、发布快照与数据库设计 |
| 原站视觉与阅读功能 | 组件和样式复用最多 | 需要适配原样式；MVP 未必覆盖原站所有阅读功能 |
| 写作后台建设 | 当前基础为零，仍需新建编辑器、上传、认证和存储 | 同样需要新建；独立目录已有实现工作进行中 |
| 数据层与发布 | 替换 Collection/getStaticPaths 与构建导入耦合 | 直接建立动态读取；旧导入链保留在原站 |
| 搜索和 SEO | Pagefind 不能天然随动态保存更新；RSS/站点地图需改读发布数据 | 搜索、RSS、站点地图需按新系统实现 |
| 部署成本 | 需从静态托管转为服务器或合适的运行时，并持久化数据库 | 同样需要服务器及持久化目录；新计划使用 Node 24 + SQLite |
| 回归风险 | 数据流改造涉及现有路由、列表、搜索和部署 | 原站可继续保留；新系统需要补足阅读和迁移回归 |
| 长期维护 | Astro 的模板与生态继续可用，另有后台需要维护 | 少量运行组件，但手写 HTTP/会话/前端意味着更多应用代码由项目自行维护 |
| 回退能力 | 应先分支或隔离目录验证，保留原版本 | 本轮已在独立目录开发，容易保留原站回退 |

不能据此声称 B 的总工作量一定低于 A；共同的大头是写作后台、数据库、发布权限和迁移。B 的主要优势是新内容链路的边界清楚，并能在不扰动原站的前提下验收。

## 复用清单

| 资产 | 处理方式 |
| --- | --- |
| 原始 Markdown 与现有生成稿 | 保留两份对照；明确哪一份作为迁移正文，避免再次自动编号或丢失原 frontmatter |
| 标题、摘要、分类、标签、课时顺序 | 建立字段映射；分类不要仅并入标签后丢失独立含义 |
| 原 URL 与目录结构 | 留存 `旧地址 → 新文章 ID/地址` 映射，正式切换时提供重定向 |
| 阅读排版、目录、主题、代码复制 | 复用设计与适配后的实现；不要求为了换内容层把阅读体验降级 |
| SEO、RSS 与站点地图 | 复用字段和路径约定，改为只查询已发布快照 |
| 代码语言归一化 | 提取可用映射；原内容中 `cpp` 593 处、`c` 505 处、`bash` 235 处、`asm` 51 处、`cmd` 43 处围栏，需按实际内容兼容 |
| 旧导入器 | 仅作为一次性迁移的参考，移除清空生成目录、剥离元数据和自动改写正文等日常保存副作用 |
| 历史日期 | 保留来源和是否真实的标记；实际保存/发布时间使用独立字段 |

## 迁移路径与正式切换条件

1. 先验收新系统的创建、上传、编辑、保存、预览、发布、撤回和重启持久化。记录限制，选择最终阅读模板与部署环境。
2. 冻结并备份原始 Markdown、生成 Markdown、日期与草稿规则、媒体、现有 URL 清单；建立迁移清单，而非直接对 253 篇执行公开发布。
3. 在隔离数据库试迁为草稿，保存源相对路径、原 frontmatter 与迁移 ID；批量脚本若不具备幂等性，重复执行前必须防止重复文章。
4. 核对 253 篇的数量与正文，检查标题、分类、顺序、日期、草稿状态和重复文章。未知字段保留来源，不能无声丢弃。
5. 对图片、相对文章链接和标题锚点建立映射。单独上传 `.md` 不会自动上传本地图片；缺失引用必须有清单。
6. 抽查长文、C/C++、汇编、命令行、行内/块公式和 Mermaid；预览和公开页一致。浏览器同时验证桌面、窄屏与中文文件名。
7. 补齐需要保留的搜索、分类、RSS、站点地图、主题、阅读工具和旧 URL 重定向；做数据库备份恢复演练与正式环境认证检查。
8. 在获得正式迁移/切换指示后再操作实际内容和线上入口；本轮授权落实为新目录验证和路线建议。切换前保留原站及回退步骤。

### 实际交付与限制

| 项目 | 实际能力 | 仍需补齐 |
| --- | --- | --- |
| 内容服务 | Node 24 HTTP + SQLite 落盘；动态生成公开页，无发布构建步骤 | 当前只绑定 `127.0.0.1`，Host/Origin 只接受本机；外部分享需要正式部署配置 |
| 写作台 | Markdown 文本编辑、双栏预览、工具栏、字数、自动/手动保存、发布/撤回 | 不是完整富文本编辑器；没有历史版本恢复、离线缓存或多人协作 |
| 文件上传 | 浏览器读取 `.md/.markdown` 后发给已认证导入 API；中文与 BOM 可解析；始终导入为草稿 | UI 文件上限 1.9 MB；没有附件、目录/ZIP 上传 |
| 数据与冲突 | 草稿和发布快照分离；数据库版本号阻止旧版本覆盖 | 版本号不等于版本历史；数据库备份恢复仍需正式演练 |
| 渲染 | 服务端统一预览与公开渲染；Shiki、KaTeX、Mermaid 本地资源 | 图表目前指 Mermaid；原始作者 HTML 不保留，需要抽查旧文是否依赖 HTML 展示 |
| 长文阅读 | 文章页、预计阅读时长、目录、公开 Markdown 下载 | 相比原站，未提供完整搜索、专题归档、RSS/站点地图、深浅主题、原阅读增强工具 |
| 迁移元数据 | 原 frontmatter 存入 `source_metadata`；来源日期未冒充真实发布时间；站主导出已补充来源字段并覆盖当前标题/摘要/标签 | UI 只编辑标题/摘要/标签；分类、课时顺序不具备独立展示。公开导出仅含发布快照标题/正文 |
| 批量导入 | `scripts/import.mjs` 递归导入为草稿并保存源相对路径 | 重复执行会生成重复文章；未提供幂等检查、URL/媒体迁移及完整失败回滚，不是已完成的 253 篇迁移工具 |
| 认证 | 单作者密码、HttpOnly/SameSite 会话、来源校验、进程内限流 | 会话与限流只在内存；正式环境仍需 HTTPS、代理/域名策略和运行维护 |

这些缺口不妨碍评估新写作链路，但不能将“本地 MVP 通过”表述为“已达到原站全部功能或已可公开上线”。

## 最终推荐

根代理补充：已完成真实浏览器 Markdown 文件上传、编辑保存、刷新保留、发布后阅读及未发布修改隔离；截图确认公式排版和 Mermaid 节点/连线显示，并检查最终默认实例的手机宽度文章首屏。详细范围与限制见 [浏览器验收记录](./browser-acceptance.md)。

**推荐 B：在新目录按动态内容架构继续开发，复用原站文章和阅读资产；不在原静态导入链上直接叠加写作后台。**

依据是当前真正缺少的功能集中在内容存储和写作发布链路，原站没有可直接扩展的后台基础，而且日常导入会重写生成目录。新 MVP 已用真实 SQLite 和 HTTP 测试证明上传、保存、草稿隔离、即时发布与重启持久化可以形成独立闭环，因此这条路线有实际运行证据支持。独立目录也让原站继续作为对照和回退版本。

这项推荐针对内容架构和开发边界，不要求永久使用当前手写 HTTP 实现。若后续最看重完全保留原 UI，可将原 Astro 阅读组件接到同一动态内容服务并采用 SSR；A 在技术上同样可行。没有必要为了“非静态”而放弃所有现有阅读代码，也不能假定轻量原生服务的长期维护一定更省。

下一步应先补齐写作可靠性的浏览器回归与所需阅读能力，再完成可对账的内容迁移及部署准备。当前应交付可运行的新目录、评审和启动说明；保留原站与全部原文。本轮不执行线上切换，也不把 253 篇笔记自动发布到新站。
