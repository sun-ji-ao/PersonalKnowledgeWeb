## 黄金样例如何使用

[cases.json](./cases.json) 包含 15 项人工编写的输入和预期结果；JSON 转义还原后的字符串就是完整 Markdown/HTML，inputHex 表示原始字节。每项给出入口、资源映射（如有）、预期规范 HTML、状态、诊断码和验收目的。metadataSubset 表示必须保留的元数据子集；诊断码按集合比较，不要求遍历顺序一致，实际诊断还须提供位置和说明。

第 2 批实现时：把输入传入真实共享转换器 → 精确比较 htmlSource → 核验元数据子集、状态和诊断 → 对成功源 HTML 再规范化一次，检查幂等 → 比较代码/公式/图表解码后的源文本。分别经 CLI 和单篇函数运行 Markdown 样例，比较结果。不能让转换器读取 expected 生成输出。

当前完整性检查命令（仓库根目录）：

```powershell
node doc/technical-notes-lab/batch-01/check-fixtures.mjs
```

此命令只检查 JSON 契约、唯一编号、输入编码、预期状态和必要字段，**不运行转换器、不校验清洗器安全、不证明 HTML 编辑器往返通过**。其日志见 [fixture-check.txt](./fixture-check.txt)。

## 各批必须补充的运行测试

| 目标批次 | 测试场景 | 通过条件 |
| --- | --- | --- |
| 2 | 编码、未闭合 YAML、重复键、非对象和超限别名 | 明确拒绝并定位，不创建假成功结果 |
| 2 | 不同代码别名、内部空行、非法语言名、重复/非法锚点 | 保留源码；清楚报告归一化与修复 |

| 5 | 展示失败、新草稿、撤回、来源下载和公共搜索 | 公开数据仅来自验证通过的发布修订；原件需认证 |

这些场景是后续验收要求，目前均未声称通过。

## 基线证据与恢复边界

- [environment.json](./environment.json)：Node/npm、Git HEAD、捕获时间及源码 ZIP 哈希。
- [source-manifest.json](./source-manifest.json)：新站 14 个源文件的路径、长度及 SHA-256。
- [source-baseline.zip](./source-baseline.zip)：同一组源码的实际快照，含锁文件和原测试；不含 node_modules、数据库、密码或 .env。
- [protected-manifest.json](./protected-manifest.json)：253 篇原始 Markdown 的哈希，验收时再次比对。
- [baseline-test.txt](./baseline-test.txt)：本批实际执行的旧 MVP 回归输出。
- [baseline-check.txt](./baseline-check.txt)：源码、旧文、快照与语法检查结果。

新站尚未纳入当前 HEAD，因此只记 Git 哈希无法恢复新站，必须保留源码快照。若需恢复，将 ZIP 解压至一个新建的空目录，对照 manifest 核验全部文件，再按锁文件安装依赖；不应直接覆盖当前工作目录。`.gitignore` 是隐藏文件，归档已单独核验其存在。

这是代码基线，不是运行数据备份。默认 SQLite 文件处于已有进程占用状态，本批未停止该进程，也未完成数据库哈希或一致性备份；不能用这个 ZIP 恢复作者的数据。数据库与原件/媒体联合备份演练在第 3 批执行。基线测试自身使用独立临时 DATA_DIR，结束后清理测试目录，不访问默认数据目录。
