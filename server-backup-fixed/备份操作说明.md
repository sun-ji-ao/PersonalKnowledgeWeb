# 服务器备份操作说明

更新日期：2026-10-04。按当前 server_backup.py 和 test_server_backup.py 编写。

本说明用于下次在原服务器进行维护模式备份。按顺序完成：准备 → 启动 → 等待完成 → 校验 → 检查服务 → 保存备份。

## 一、先确认在哪里输入命令

| 位置 | 用途 |
| --- | --- |
| Windows PowerShell | 必要时上传脚本和说明 |
| 服务器 SSH 终端（提示符类似 sunjiao@10-11-6-94） | 预检查、执行备份、看日志、校验和检查服务 |

脚本实际运行在 Ubuntu 服务器，不是在 Windows 上运行。服务器当前目录是 `/home/sunjiao/server-backups`，注意末尾有 s；不要混用旧说明中的 server-backup。

每次 backup 都是全量备份，生成新目录，不覆盖旧备份，不自动清理旧文件，也不自动重试。通常会备份根分区、独立 /boot 和 /boot/efi。

**执行时会暂停网站、Nginx、VPN、NewAPI、数据库、记录服务和其他当时运行的 Docker 容器。请安排维护时间，并通过公网 IP 直连 SSH，避免依赖 VPN。** 脚本在结束或普通异常时尝试恢复原服务；仍需最后检查。

## 三、每次备份前检查（服务器）

```bash
cd /home/sunjiao/server-backups
sudo python3 server_backup.py preflight
df -h .
sudo systemctl status server-full-backup-v2.service --no-pager
```

确认预检查列出预期分区、程序目录和待暂停服务。preflight 不会停止服务，也不代表后续所有检查都已经通过。backup 启动时还会按源文件系统已用空间加 5% 做保守空间检查；磁盘空间要为历史备份和新备份留足余量。

如果任务状态是 `active (running)`，已有备份正在运行，直接看日志，不要再次启动。首次执行或之前任务已被清理时，状态命令可能显示找不到单元，这不影响新任务启动。

## 四、启动备份（服务器，只执行一次）

完整复制下面命令；反斜杠必须是每行最后一个字符，后面不要添加空格：

```bash
sudo systemd-run \
  --unit=server-full-backup-v2 \
  --collect \
  /usr/bin/python3 /home/sunjiao/server-backups/server_backup.py \
  backup --maintenance
```

看到 `Running as unit: server-full-backup-v2.service`，说明独立任务已启动，不代表备份完成。它由 systemd 管理，SSH 断开后仍可继续。

如果报告同名单元已存在，先用上一节的 status 检查，不要反复启动或强行停止任务。脚本也有运行锁，禁止多个备份/恢复操作同时执行。

## 五、马上查看日志，等待完成（服务器）

启动命令返回提示符后，立即执行：

```bash
sudo journalctl -u server-full-backup-v2 -f
```

`-u` 指定任务，`-f` 持续显示新日志。可以看到：

```text
Backing up filesystem: .
Backing up filesystem: boot
Backing up filesystem: boot/efi
Backup complete: /home/sunjiao/server-backups/backups/本次时间戳
```

根分区打包可能几分钟没有新输出，之后计算校验和也可能耗时。此前一次备份约 7 分钟，仅供参考，数据量和机器负载会影响时间。

出现 `Backup complete:` 才表示备份流程和自动服务恢复步骤已完成。**记下这行里的完整目录路径，后续校验使用这个目录。** 按 Ctrl+C 退出日志查看，不会停止备份。不要在 journalctl 窗口未退出时输入下一条命令。

如 SSH 断开，重新登录后可查看近期日志和状态：

```bash
sudo journalctl -u server-full-backup-v2 -n 100 --no-pager
sudo systemctl status server-full-backup-v2.service --no-pager
```

日志可能包含以前使用同名单元的运行记录，判断本次结果时核对启动时间和备份目录。`active (running)` 表示任务仍运行。因为使用了 `--collect`，任务结束后可能找不到单元，此时检查日志。`ERROR` 或 `Failed with result` 表示本次任务出错，应转到第九节。

## 六、校验本次备份（服务器）

先设置本次目录变量：将下方“替换为本次时间戳”替换为刚才 `Backup complete:` 输出的目录名。不要使用旧目录，也不要保留占位文字。

```bash
BACKUP_DIR='/home/sunjiao/server-backups/backups/替换为本次时间戳'
printf '准备校验：%s\n' "$BACKUP_DIR"
```

确认打印的路径无误，再执行：

```bash
sudo python3 /home/sunjiao/server-backups/server_backup.py verify "$BACKUP_DIR"
VERIFY_EXIT=$?
printf '校验退出码：%s\n' "$VERIFY_EXIT"
```

校验会读取全部压缩包，核对文件大小、SHA-256，并完整解压读取 tar；可能几分钟没有输出，请等待。

**成功条件：命令正常输出清单，包含 `"complete": true`，且“校验退出码”为 `0`。** 有 ERROR、校验退出码非 0 或清单未完成，均不能作为有效备份。不要手动修改 complete。

BACKUP_DIR 变量只保留在当前 SSH shell 中。重新登录或换窗口后需重新设置它。校验通过证明备份文件通过完整性检查，实际恢复还需在独立环境演练。


按当前部署，四项 systemd 服务应都显示 active；codex-recorder-recorder-1、new-api、new-api-postgres 应运行且 healthy；两个健康接口应分别返回 `{"ok":true,"mode":"html"}` 和 `{"ok":true}`。若以后应用改版，响应字段可能变化，应按实际部署确认。

记录服务重启后，其记录开关可能回到 OFF，需要在公司电脑上按需重新开启。备份脚本不会操作该开关。

## 八、查看大小和保存备份

仍在设置过 BACKUP_DIR 的服务器窗口执行：

```bash
sudo du -sh "$BACKUP_DIR"
sudo ls -lah "$BACKUP_DIR"
```

保存或传输整个时间戳目录，包括 manifest.json、所有 fs-*.tar.gz、打包日志、service-state.json、server_backup.py 和使用说明.md，不要只取根分区压缩包。当前三分区布局通常会生成 fs-000、fs-001、fs-002 三个包；挂载布局变化时，以清单为准。

备份含密码、SSH/TLS 私钥、记录密文和解密密钥，整体未加密，应保存在权限受控的备份服务器或加密存储，传输使用 SSH。原服务器上的一份备份不能防止整台服务器或磁盘丢失，建议另存一份，并在目标端再次执行 verify。程序不会自动上传备份。

## 九、失败或服务未恢复时

先查看任务日志：

```bash
sudo journalctl -u server-full-backup-v2 -n 200 --no-pager
sudo ls -lah /home/sunjiao/server-backups/backups
```

找到本次失败任务对应的时间戳目录，核对时间，不要误选历史成功目录。设置 BACKUP_DIR 后读取打包日志：

```bash
BACKUP_DIR='/home/sunjiao/server-backups/backups/替换为本次失败目录的时间戳'
sudo ls -lah "$BACKUP_DIR"
sudo cat "$BACKUP_DIR"/fs-*.log
```

如果错误发生在打包前，目录或 fs 日志可能不存在。不要删除失败目录，也不要反复重新备份。

如第七节检查表明服务未恢复，且本次目录中有 service-state.json，在确认原备份任务已停止后执行：

```bash
sudo python3 /home/sunjiao/server-backups/server_backup.py resume "$BACKUP_DIR"
```

然后重新执行第七节检查。resume 只按本次记录恢复原服务/容器状态，不会续传压缩包或补完备份，也不会开启记录开关。只能在原服务器使用。服务已正常恢复则无需执行 resume。

如果仍失败，保留任务日志、fs 日志和 service-state.json 供排查，不要直接忽略 tar 错误或强行修改清单。

## 十、备份范围与限制

包含源系统已挂载的受支持本地文件系统中的系统文件、应用、配置和持久化数据，并保存权限、ACL、扩展属性、硬链接和符号链接。

不包含 /dev、/proc、/sys、/run、/tmp、/var/tmp、lost+found、交换文件及整个 `/home/sunjiao/server-backups` 工具目录。工具目录内的旧备份不会重复打包；脚本和说明单独复制到新目录。

维护模式额外排除 `/var/log/auth.log` 和整个 `/var/log/journal`，包括 journal 历史，避免持续写入导致打包失败；其他文件发生变化仍报错。离线只读模式不增加这两项排除。

这是一套文件级备份，不含分区表、引导扇区、内存、未挂载磁盘、外部存储、云安全组、公网 IP 和 DNS。维护模式只暂停已知应用，不保证运行中的操作系统完全不写磁盘。新增写数据的宿主机服务需按实际情况增加 `--stop-unit 服务名.service`。

本说明专注日常备份，不提供生产恢复命令。**不要在正在使用的原服务器上执行 restore。** 迁移恢复应使用离线目标磁盘，并另行核对目标的网络、磁盘、内核、引导和应用环境。
